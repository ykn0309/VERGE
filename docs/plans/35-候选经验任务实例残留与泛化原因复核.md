# 候选经验中的任务实例残留与泛化原因复核

## 1. 问题与范围

用户指出最严重的问题可能是经验的content/trigger使用“如xxx”引用本task例子，削弱通用性。本轮只读复核计划32的100条真实运行：全部63条Critic候选、46次准入PASS、15次Fusion及最终13条经验，结合原task/偏好对、实际system/user、Admission理由、应用标准和两次融合历史定位机制。不修改提示词、方法、历史Memory或日志，不新增实验/自动过滤器。

计划32运行时的实际system保存在role_io，而当前源码已另有统一经验列表和rubric术语替换；本次原因分析优先引用该运行真实消息。这两处后续修改没有处理实例抽象，不能算作泛化改善证据。

结论：**现象存在，而且部分task/回答实例已被保留到Memory。关键缺陷是没有把单个任务的诊断抽象成可替换实例的评分标准设计方法；“如”只是常见表现，不能直接等同过拟合。**

### 3.2 有例子但抽象程度相对较好的对照

- **2766重生成**将第一版“本例为8/任何长度不等于8”改成“目标长度数值”，trigger改成“X letter words”。句型仍有例子，但关键数字已成为变量，可以用于其他指定长度任务。未指定长度时推断固定长度的额外条款仍有别的语义问题，不因参数化而全部合格。
- **2759**保留“机构名称、年份、地域”和“A机构/B机构”作为方法说明，没有把实际GEPF/CDPQ机构名写入经验。它的文档访问前提另有问题，但就实体抽象而言优于2818。
- **2857/2817合并**将邮件要点、笔记题目抽成输入依赖缺失；正文和trigger仍带each point/from notes等短语示例，但可以覆盖多种依赖原材料的任务。短语不应被当成穷尽的触发关键词。
- **2896**保留后台操作类型，未固定“30分钟/买牛奶”；能力边界条件比具体任务实例更有可迁移性，仍须依据实际工具能力判断。
- **2874**未保留3台笔记本、2个显示器、1100/200等数值，提炼成数值计算不强制要求未指定的过程展示；trigger的Calculate total cost短语可去掉以减少措辞依赖。

因此，需要区分必要任务类型/领域条件、可替换结构例子和多余实例细节。通用性应指在同类不同实例中成立，不必强迫每条经验跨所有领域适用，也不应把不同设计问题合成空泛的“回答应准确完整”。

## 4. 原因定位

### 4.1 Critic缺少从实例到设计方法的抽象要求

实际Critic system要求“content表达具体连贯的标准设计方法”“允许上下文、领域知识推理及同一目的的协同动作”，但没有要求：

- 把当前task的实体、数量、时长、措辞替换成其语义角色或任务提供的参数；
- 区分只应留在私有analysis里的诊断例子与公开content/trigger里的方法；
- 检查换一个同类对象/数值/场景后，该经验是否还成立；
- content只规定如何构建/核验标准，而不提供当前题目答案或方案。

明确禁止的仅是“候选回答特有内容、偏好身份、私有评分或比较结论”，**没有禁止不必要的task实例残留**。模型于是容易用“当任务属于某类（如本task对象）...”的句式表达“可复用”，以通用开头包住仍固定本例的正文。2818甚至越过已有回答细节禁令，说明既有禁止项的执行也不稳定。

### 4.2 原始证据高度集中于当前任务，局部诊断容易进入候选

Critic实际输入包含完整task、两份回答、失败标准与Judge结果；第二轮还包含上一候选和前后实际标准/结果，拒绝重生成包含被拒候选与理由。用于诊断的信息充分，但没有一个明确的“从这些证据只输出可迁移设计动作”的生成约束。

私有analysis和公开候选在同一次响应中生成。模型可先针对具体差异解释失败，再把同一差异改成“如...”案例；2818的对象对照、2586的日期对照、2784的主题对照都能在真实输入中找到来源。第二轮仍然依据同一个任务的失败/成功方向收敛，故未主动抽象时容易继续增加本例细节。

这是输入与输出目标之间的设计缺口。不能据此推断应该删掉诊断所需证据；更合理的是在Critic自身输出阶段明确实例到方法的转换。

### 4.3 Admission把“对当前任务适用”误当成“可迁移”

实际system强调“限定任务类型、具体指导或多个协同动作本身不足以拒绝”“不能仅因复杂、具体...而拒绝”，目的是避免把合理专业经验一概挡住。但没有清楚划分必要领域边界与不必要的样本常量，也没有要求核对条件中更换实例后是否仍匹配content。

实际理由显示：

- 2527/R2G2：因为遵循“3天/45分钟/虎门销烟、林则徐”就称具有“高度可复用性”；
- 2922：将必须写NBA的规则称为通用事实骨架，并称没有保留样本细节；
- 2586：直接含January1,1901/1901-2000，却判定“未包含...保留样本细节”；
- 2556：明确说“紧扣任务目标”，未处理trigger多个领域与content固定NLP的范围冲突。

这些是日志可直接验证的误判。Admission会拒绝别的缺陷，但经常不要求重生成去掉本题锚点，所以具体性被当作优点，泛化边界未落实。

### 4.4 应用成功与信用检验的目标没有覆盖迁移

入池资格是Admission PASS+声明采用C+**同一任务**的实际Judge成功。候选中的题内对象、数字、对比细节正好可能帮助Generator在这个任务上构建区分标准；2818的应用标准明确复用了“庭院加热器”，2586继续核验本题日期表达。

P/N计算也只依据引用标准在当前偏好对中的判别差，不考虑本例细节是否可以替换。因此这条路径对通用表达没有额外选择压力：一条携带当前题目信息的经验可以获得合法成功/信用。后续R0维护有机会提供不同任务的弱证据，但本次仅2/13经验有非零下游事件，且仍受来源自报/Judge误差影响。

这说明验证范围与通用性目标不同；不证明这些例子实际导致成功，也不能量化移除例子后的效果。

### 4.5 Fusion负责去重，ADD原文保存，不会自动抽象

Fusion实际system定义职责为“识别候选与已有经验是否重复”，默认ADD。代码`ExperienceMemory.fuse()`明确要求ADD使用candidate原文；13次ADD不会调用改写步骤来消除实例残留，空池首条甚至不需Fusion后端请求。这是有意保持被应用候选与入池文本一致的契约，不是存储错误。

MERGE虽可改写，也没有对task常量参数化的要求。2817的合并扩大了输入依赖方法；2784合并时则把题内压力管理/工作生活界限对照保留下来，融合后的trigger依然依赖已观察回答。Fusion不能承担先前未完成的抽象。

若只在成功后删例子重写文本，会使入池对象偏离实际被应用对象；抽象更应在Critic提出、Admission通过之前完成，而不是用未经应用的清理版本替换已验证原文。

## 5. 后续修改方向（本轮未实施）

1. **Critic**：要求content/trigger直接表达任务结构、适用边界与设计动作；把原题例子放在私有analysis，实体和数量由新task提供，不在公开经验中写入本例。保持必要领域知识与条件，避免空泛化。
2. **Admission**：继续允许任务类型专门经验，同时检查“通用trigger+本例固定content”的不匹配，以及换主体/数值后原则失效的样本锚点；具体原因反馈Critic，不另加审查角色或词语过滤器。
3. **Fusion**：合并时保持方法与条件的一致抽象层级，不用拼接原题例子扩充经验。ADD保持原候选文本，靠前序抽象保证质量。
4. **评价解释**：将单任务验证和迁移证据继续分开。现有100条只做诊断，不追溯改写池文本或credit，也不因“如”出现就判定全部无效。

以2818说明合理抽象方向（示意，不是本轮改写产物）：

```text
trigger：任务要求围绕指定对象或场景提出建议。
content：设计评分标准时，单独核验回答的主体与任务指定对象是否一致，
并依据该约束对任务目标的重要性安排权重；避免让泛化的内容质量维度
掩盖回答针对错误对象的问题。
```

这一表达仍明确指出“检查什么、如何安排评价”，但不需要橱窗灯、电视屏幕或庭院加热器。对2622，保留“时长受限的对话脚本”条件，将时间预算从task中取得，而不是所有任务一律25词、4句、10秒。
