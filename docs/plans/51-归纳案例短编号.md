# 计划51：归纳案例短编号

2026-10-13。用户指出27组复测第15组的ID抄写负担，要求用1、2、3等简单编号。

## 证据与范围

原第15组第一次与第二次均将64位案例ID中的`...ea960ac...`抄为`...ea96ac...`，第三次又删除两个ID的`helpsteer3:train:`前缀。可确认直接失败是ID抄写，不是缺少归纳方法；长ID增加复制负担，但短编号也不能保证模型永不遗漏/重复。

只修改归纳员的结构化案例标识，不改变任务、回答、标准、Judge证据及P/N。原27组复测结果不重写，也不因本次修改自动再发真实请求。

## 实现

- 扩展已有NumberedIDCodec的sample命名空间，将输入cases中的sample_id按稳定顺序映射为`"1"`、`"2"`等短数字字符串。模型输出仍用sample_ids字段，程序严格映射回原ID后才进行完整唯一归属检查与存储。
- 模型若返回JSON整数1/2，沿用已有数字ID类型规范化；零、负数、布尔值、未知编号及原长ID不猜测还原，不增加旧协议兼容。重复/遗漏仍沿用有限结构纠错。
- HTTP原始消息和回复记录短编号，Memory/trajectory及拆分案例仍记录真实ID；不改原自然语言文本。100,000字节预算按实际投影消息核验。
- 独立复测脚本同样投影短编号并还原输出，防止它绕过生产调用的标识转换。
- Prompt=`local-credit-bounded-experience-common-method-numbered-cases`；Manifest6/Trajectory6/Memory4不变，禁止跨Prompt续跑。AGENTS的固定项目目标和文档入口不改。

## 验证与下一步

288项离线测试通过。新增HTTP模拟覆盖长ID输入不泄入结构化模型消息、字符串/整数短编号、逆序分组还原与拆分保存，以及未知/原长ID/重复/遗漏/零/布尔值失败不写Memory。已有有限纠错、超长文本接受和完整HTTP链路测试保持通过。

后续用户要求审查其他全部角色的长ID：Selector、Generator、Judge、Critic均已有数字映射，没有发现其他结构化长ID入口；Embedding不携带程序ID。加强现有完整HTTP场景，收集实际UUID经验/候选/标准集/标准及64位案例ID，断言全部五角色消息（含Critic第二轮历史/反馈）不包含这些真实ID，同时验证存储仍保持正确案例归属。288项测试再次通过；没有修改生产逻辑或再发真实请求。

这只解决标识复制负担，不修复计划50的语义问题。计划50旧无需拆分16组仍有12组拆分，合理分化10组有4组改为一条、1组无效；第25组共同角色归属方法更集中，第16组合并丢失摘要忠实性，第24组条件化回答淡化。不能把拆分率下降解释为归纳质量普遍提升。

后续建议先在少量近似方法、必要差异及错误证据案例上做输入对照，检验当前经验文本的锚定影响，再决定是否改变归纳输入；同时检查单条方法是否保留每类案例必要动作。该假设尚未验证，本轮不实施新语义机制、不新增analysis或真实实验，也不改已有复测产物。
