# 16 — v16 Chat Hard 首次成功率诊断

## 范围与结论

数据：`runs/rewardbench-chat-hard-qwen-vector-full-train-v16-resume2/artifacts/` 的 456 条完整轨迹、真实 role_io 和最终经验池；任务来自 `runs/rewardbench-chat-hard-data-full/train.jsonl`。参照旧版 `runs/rewardbench-chat-hard-qwen-vector-full-train-resume1/`，逐 sample_id 配对。仅离线分析，没有额外模型调用或代码改动。

**直接现象是标准失去区分能力、平分大幅增加。** 可复核的问题包括 Judge 缺任务上下文及明显误判、Generator 的不必要要求/缺失输入处理不足，以及经验的弱区分力与事后 trigger。由于 Generator 提示词、Judge 提示词、独立判断协议和经验池同时变化，目前不能量化各项因果贡献，也不能断言独立 Judge 本身应该撤回。

## 1. 数值：下降主要表现为平分增加

| 初始结果 | 旧版 | v16 |
|---|---:|---:|
| chosen 得分更高 | 327（71.71%） | 255（55.92%） |
| 平分 | 40（8.77%） | 114（25.00%） |
| rejected 得分更高 | 89（19.52%） | 87（19.08%） |

净少成功 72 条；平分多 74 条，反向判别少 2 条。这是结果分布的描述，不是把 74 条都归因于 Judge。配对后：旧成功→新失败 111 条（其中 69 平分、42 反向），旧失败→新成功 39 条。

v16 的 114 个平分中，113 个每项 Boolean 均相同，只有 1 个是正负贡献抵消。36 条两侧全 true，35 条两侧全 false。因此，不是主要由浮点误差或权重抵消导致；只是调权重不能区分两侧相同的 Boolean。

全部 1,651 条初始标准中：两侧相同 1,009（61.11%），仅 chosen 满足 452（27.38%），仅 rejected 满足 190（11.51%）。旧版两侧相同 647/1,703（37.99%）。

## 2. Judge：上下文缺失与语义误判

`verge/prompts.py:237` 的 `judge_payload` 只发送 criteria 和 response，**没有 task**。若问题引用“引号内文本”“给定笔记”“用户要求”，Judge 未必有事实依据核验。这个缺上下文问题在旧版也存在，不是 v16 新引入；旧联合 Judge 还能看到另一份回答和 chosen/rejected 标签，可能获得相对比较线索，亦可能带有标签偏置。

已核对 456 条初始判断的两侧：912/912 个实际 role_io 输出与最终轨迹相符，未发现并发结果交换或反解把 true 变为 false。格式错误为 0 不代表语义正确。

具体案例：

- `llmbar-adver-manual:2926`：task 要求统计给定引文词数，chosen=`23`、rejected=`42` 加无关解释。初始标准问准确计数和计数范围；Judge 收到的只有标准与回答，看不到引文，两侧均 false。
- `llmbar-natural:2585`：task 的四项为 Inch、Kilogram、Centimeter、Yard；chosen=`Kilogram`，rejected=`Inch`。标准已经直接问“是否准确识别出 Kilogram”，chosen 仍被判 false。后续改为“最终结论是否为 Kilogram”才得到 true，显示判定对措辞/简答形式敏感，不能只用缺 task 解释。
- `llmbar-adver-GPTInst:2858`：chosen 明确有自夸和贬低用户的傲慢语气，初始“是否采用傲慢语气”却 false；“是否避免声明编程限制”两侧也均 false，而两份回答都没提限制。修订后还出现措辞变化带来的判定变化。

Judge 只有 Boolean，没有判定理由；上述原因依据输入和文本复核，不把 Critic 自己的解释当作 Judge 的真实推理。

## 3. Generator：标准未适配实际任务条件

- `llmbar-natural:2585`：task 只问哪项不同，额外要求回答呈现质量/长度分类逻辑，使正确简答的区分信号被削弱。
- `llmbar-adver-GPTInst:2817`：task 要求“根据给定笔记”生成四选项题，但实际没有笔记。chosen 请求补充笔记，rejected 编造判断题。R0 全是“已生成题目是否满足格式/正确性”，缺少当前合法行为是请求缺失输入这一分支，chosen 全 false，rejected 获得“答案唯一”分数。
- `llmbar-adver-neighbor:2759`：task 给出文档链接但尚未给问题，chosen 邀请用户提问，rejected 编造其他机构的问答。R0 强调内容提取、数据准确和章节结构，chosen 全 false；rejected 在结构项获得分数。链接内容本身未提供给 Judge，也没有抓取机制。

核心是“完成形式/解释过程”被当成普遍必要条件，而合理简答、缺输入时的澄清、事实主体一致性等关键区别覆盖不足。案例证明该问题存在，不给未经全面标注的总体发生率。

## 4. 经验：规模增长没有转化为区分信号

| 组别 | 初始成功 |
|---|---:|
| 选中经验的任务 | 127/232 = 54.74% |
| 未选经验的任务 | 128/224 = 57.14% |

两组任务不随机同质，不能用此表证明负迁移。带经验来源标准共 353 条：正方向 88、零方向 219（62.04%）、负方向 46；未标来源标准的零方向为 790/1,298（60.86%）。因此大量经验引用没有产生区分信号，不能把 108 条池规模当成效果证据。

335 次“任务×选中经验”使用，downstream credit 正/零/负分别 84/206/45。零贡献不更新 Beta 状态；修订信用则有 130 正、5 负记录。confidence 混合了标签指导修订贡献和后续使用反馈，不是未来任务成功概率。

例如最高置信度经验 `exp_58e8870a2e904786851ea32751a7bb02`（0.844）虽然累计有正信用，但 trigger 包含“初始标准未能有效区分回答”。Selector 在 R0 生成前仅有 task，无法严格核验此条件。另一高置信度经验也含“初始标准无法有效区分回答质量”。准入/筛选在这些案例中没有保持 task-only 可检查边界，经验与使用时点存在错配。

## 优先排查顺序

1. 保留独立、无偏好标签的 Judge，明确其能否获得完整 task；用固定 R0、固定回答的小规模盲审校准缺上下文、简答和否定问题的误判。
2. 再核验 Generator 的标准：任务必需条件、缺失输入分支、可独立核验性和有利方向，重点检查上述具体失败。
3. 审查已入池经验的事后 trigger、选择过宽和实际零/负贡献；检查置信度是否主要靠修订证据积累，而非稳定下游收益。
4. 对照实验保持同一 R0 和同一 Judge 协议后，才比较经验或提示词改动的作用。不为提高曲线将 tie 改成 success，也不靠更多低区分度标准或更大池替代判定质量检查。
