# Judge 独立 few-shot 复测

3个历史实际单侧Judge请求，各当前baseline/few-shot一次，6次有效、0结构重试；首次baseline有2次ReadTimeout按原有有限网络重试恢复，共8次HTTP请求，原任务/标准/回答和编号保留，原产物哈希未变。

|案例|历史|当前baseline|few-shot|评价|
|---|---|---|---|---|
|人物完整名单/计数矛盾|编号1false，补造遗漏|false，但理由最后称应True|true，但11名仍称10人|Boolean局部改善，实际计数仍错|
|吉他回答的条件化同义表达|1false/2true/3false|1true/2true/3false|1true/2true/3false|当前baseline已修正，few-shot无额外改善|
|事件结果与玩笑道歉|false/false/false/true|全false|false/false/false/true|编号3都正确；4含“鱼翻肚后”前提，few-shot忽略该前提，不能把历史true当金标|

第三例原选为正常对照：游开确实不等于翻肚，玩笑道歉确实存在。但复核完整问题后发现第4条还要求“鱼翻肚后”，回答没有翻肚；当前baseline指出前提缺失，few-shot只核对道歉性质。两变体还把帽子墨镜认定为不赤身，缺乏充分依据；few-shot声称没有放松也与回答的satisfied sigh有张力。这说明理由仍会增加错误事实，不能仅按Boolean与历史一致性计分。

两个示例均本次独立构造，未从数据集提取或改写。然而示例1的“两件”括注与3件名单矛盾，输出按真实完整性判true，可能教模型自行修正标准，存在角色越界风险。本轮运行前未及时改掉；运行后保持冻结，未换例/重跑。后续应改为无矛盾计数示例，再验证保留条件前提，**不推荐当前Judge示例直接上线**。

仅3固定历史输入，每变体一次，没有外部音乐事实核验、完整链路或因果增益证明。
