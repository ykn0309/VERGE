# 97 — 经验组织与使用流程重设计建议

2026-10-29。**状态：待讨论方案，未实施、未实验，不替代当前设计。**用户要求停止局部提示词优化，转向经验组织及整个使用流程。两模型在干净上下文中分别提出方案并接受追问，GPT全程使用magpie；原始材料保存在`artifacts/research-redesign-97/`。

> 后续讨论：用户希望保留经验直接帮助Generator，当前转向[角色指南与渐进完善98](98-角色指南与渐进完善建议.md)。本文保留为候选选择路线的比较方案，不作为当前优先建议。

## 1. 推荐方向

不再只要求模型“正确理解trigger和principle”。建议同时改变经验保存的内容、它影响决策的位置、提炼和修订的验收方式。

第一版选择一个较大胆、但能明确检验的做法：**Generator只看task生成候选评分方案；经验帮助Selector比较候选；程序按ID原样取出最终方案。**经验不能直接改标准或权重。

这改变了经验的作用：从直接参与写标准，变成帮助判断哪些标准更合适。它没有解决“怎样创造候选中没有的新检查”，不能冒称完成所有方法迁移问题。如果这个限制让合格候选经常缺失，应否定这条路线，而不是不断补抽掩盖问题。

## 2. 为什么不能只多加几个字段

已知问题同时来自四处：经验本身混有过强策略；选择时把相关当适用；使用时把条件当事实；修订时可能把方法越改越强。模型连自己的任务分析和反例判断都会出错。

因此新增字段必须改变具体决策或验收，不能只是让输入更长。完整的适用条件、失败原因或合理替代都有价值，但仍需模型理解，不能被当成程序保证。报告95已有的改写、要求ID绑定和草案修订，不应换个名字再当新方案。

## 3. 经验保存什么

建议每条经验分成四项运行内容，另存证据记录。实际字段命名可在实施前再定，不以JSON形式本身为创新。

| 内容 | 写清楚什么 | 用在哪里 |
|---|---|---|
| 适用情境 | task中哪些特点使它值得考虑 | 检索和Selector初筛；不能把“名称有错”当未经验证的前提 |
| 要识别的错误与判断关系 | 哪类标准会错罚合理回答、或漏掉真正错误；比较时应保留什么检查 | Selector比较完整候选，不是命令回答采用某种写法 |
| 边界与合理替代 | 情境改变后如何换判断；哪些不同完成方式同样合理 | 防止把有用的一种写法当唯一写法；例外越堆越多应重新整理或撤销经验 |
| 最小对照 | 一个适用例与一个条件不同的边界例，解释判断为什么变 | 帮助理解关系；不用原题专名、答案或一长串示例 |
| 证据记录（非运行正文） | 来源、原始轨迹、核实状态、版本、独立适用／边界／失败案例 | Critic、Updater和离线审查；测试Selector不读原回答和偏好标签 |

四项可以很短，不要求为了填满字段编造内容。每条仍只处理一个可独立判断的问题；不能确认是否有用的经验先保留为假设。

**不是恢复旧版填空模板。**不让Generator填参数、不检查逐字渲染，也不强制每项适用依据都必须是task原文子串。必要正确性可以来自任务本身的含义，例如人物分析所用事实不应违背作品，而不必要求用户先写“不要编造”。

## 4. SEO案例：存储与使用的完整例子

下面是拟议重建，不声称复原了原经验最初的来源：

- **适用情境：**介绍对象已有的规格、数量或组成信息。
- **判断关系：**核验属性是否准确表达；对象有多个版本，不自动表示用户要求分别创作多个产物。
- **边界：**如果task明确要求逐项分别交付，就必须核验对应产出数量；两类要求同时存在时分别处理。
- **最小对照：**“商品附带多个版本，请写介绍”与“请为每个版本分别写介绍”。前者可以用一份介绍说明属性，后者需要逐版交付。

真实task要求描述作品、SEO、注明1080×1080与3个图像变体、商用和转售权、末尾创业应用及无HTML。Generator不看经验，仅据此一次生成三套完整rubric。

假如候选A检查“描述是否注明3种变体”，候选B要求“必须生成3份不同描述”，Selector用这条经验识别B增加了交付要求，选择保留全部真实要求的A。若A又漏掉商用权利，也不能只因数量解释正确就选A，必须评价完整方案。

若三套都漏SEO或都误解数量，记录候选不足。首轮实验不补候选、不把人工正确标准塞入池中。生产是否允许有限重生成，留到该路线证明可行后再讨论。

**有用方法也要留下。**人物分析经验可以帮助选择“核对作为论据使用的剧情是否符合原著”的方案，同时拒绝“至少引用两处”。术语解释经验可以帮助拒绝无依据地强制先纠错，但不能提前告诉模型术语的正确答案。

## 5. 选择和生成流程怎样变化

1. **Generator：**只看完整task，一次生成3套完整候选，均满足现有标准格式。可以在检查组织与取舍上不同，不刻意制造坏候选；同次生成不是3个独立样本。
2. **检索：**按任务召回方法记录，主要索引适用情境和判断关系，不把原始答案或长历史拼进索引。
3. **Selector：**看到task、完整候选及相关经验，判断条件是否成立、经验能否帮助区分候选，并返回候选ID、实际参考的经验及简短依据。不是只凭主题选经验，也不是只看经验标题。
4. **程序：**只接受已有候选ID，完整保留其标准与权重，禁止Selector改写、拼接或另造一套。
5. **Judge：**继续两次独立判断，只看task、选中标准和一份匿名回答，不看经验或偏好。

常规有经验组仍约4次模型调用：候选生成1、选择1、Judge两侧各1；生成与比较的token会增加，不能称成本不变。检索embedding另计。

**真正由程序保证的：**经验没有写入最终标准文本的接口，最终rubric确实来自冻结候选集。**程序不能保证的：**候选正确、经验适用、Selector判断正确。它依然可能被经验诱导而选中坏方案。此区别必须保留在结果解释中。

## 6. Critic、准入、Updater和反馈一起调整

**Critic不再只归纳优答的外形。**它查看任务、实际候选、选择结果和评价轨迹，提出“哪两种评分判断应被区分”，附来源依据、合理替代与未知项。原始轨迹留证据记录，运行内容必须泛化。若只是task理解不明或Judge可疑，不强行造新规则。

**核对通过先暂存，不直接认定可普遍复用。**先在来源之外的适用与边界案例上检查它是否真的帮助比较；来源题成功只是线索。具体数量和门槛在实验前预定，不把任意小样本数当理论保证。

**Updater不能只靠加例外过验收。**修订要指出改变了哪项判断关系、为什么、可能影响哪些旧案例。保留版本；比较旧有效例、边界例和没给Updater看的任务。不能让修复一题抵消新的明确越界，也不能凭同批回放提高就宣称迁移更好。初版不自动扩展成庞大依赖图或拆分系统。

**证据不再等于逐标准引用方向。**保存候选池、实际选用的经验集合、候选ID、适用判断和评价结果。实验中与同池无经验选择配对，报告两组选择和质量的差异；不能把整组差异分摊给每条经验，理由和引用也不是因果证明。需要单条判断时另做移除对照。

旧版本和旧Q保留归档，但旧Q不能作为新经验可信度直接继承。贝叶斯模块先不重设计、也不恢复正式参数估计；待新经验和反馈对象明确且有局部价值，再讨论怎样建模。

## 7. 第一步怎么验证

先做一个小规模完整原型来验证表示与选择，不重训、不重写86条池。可先整理约8—12条经验，覆盖术语／实体、对象数量与交付数量、原文依据、格式、回复／续写等；每条以现有来源与边界证据核对。这是人工或代理核对内容后的可行性试验，不代表自动Critic已经学会生成新经验。

预先固定至少24个不同历史任务，覆盖适用、边界、正常和原有改善案例；经验编写用到的案例与实验任务分开，预选20题确认集保持未用。它们仍是开发材料，不称盲测。各变更模块至少20个代表性真实输入独立检查；选择与生成分别审查，不直接用完整训练结果掩盖模块错误。

每题先固定无经验生成的候选池，所有组看到相同候选、同模型、同样顺序，在组内重复时平衡位置偏差。四组都只能选ID：

| 组 | 给Selector的经验 |
|---|---|
| A | 不给经验，仅根据task选 |
| B | 当前双字段原经验 |
| C | 核对修正后的普通文本，包含完整关系、边界和对照 |
| D | 与C相同的信息，按新结构组织 |

A/D看经验是否真的帮助选择；B/C看修正内容的作用；C/D看结构呈现是否额外有用。四组权限相同，**这一步不能单独证明“禁止写入”比自由生成更好**；以后需与等计算预算旧流程再比较。所有组共享候选，防止把多生成方案带来的收益算给经验。

同时检查：

- 候选中是否至少有一个合格方案；有而没选对，与全都不合格分开报告。
- 最终标准有没有乱加要求、漏task要求、删除必要正确性检查、错罚合理替代。
- 必要核验是否保留；不用引用率下限替代效果。
- 实际回答对的区分及正常题退化。相同候选的Judge结果可按事先定义的缓存规则跨组复用，重复之间独立，不挑有利结果。
- 调用、token和拒绝选择／候选不足情况；有争议的事实与任务理解保留待判，不把模型审核当真值。

**应当放弃或简化的情况：**合格候选经常不存在；有合格项却仍经常被经验引向坏项；D不优于C则不主张复杂结构有价值；经验组不优于A则不继续宣称经验有效；只在退化题改善而伤害正常题则不采用。阈值、预算和样本细节应在真正启动前明确。

## 8. 两模型建议如何取舍

本轮两方均通过magpie、新上下文、只读工具独立分析，再分别接受主代理质疑。Sol提出经验辅助候选选择；DeepSeek原先建议任务要求说明、经验附着子检查和试用账本。

主代理没有采用后者的主要保证：无独立权重的子检查仍可否决高权重标准，附着不等于没有新增义务；自由生成又不能由程序证明只来自任务要求。同一Judge调用中的试用检查还可能影响基础判断。DeepSeek追问后承认这些限制。

两方澄清均接受候选选择路线值得对照，但意见不等于证据。DeepSeek推测候选大概率缺少有用检查，尚未实验；这恰好应成为第一轮实测的覆盖问题。候选一次输出3套会增加token，不必等于调用次数乘3；若换更强模型生成候选，则要单独标明，不能混入结构效果。
