# 98 — 角色指南与渐进完善：双模型讨论建议

2026-10-29。**状态：角色指南与逐经验说明已按计划100实现并复测；以下保留形成方案时的讨论，实际协议见当前设计，效果见报告100。**GPT-6.1 Sol high与DeepSeek V4.1 Flash max均通过magpie，在新会话分别完成分析和一次澄清；原始材料与回复留存`artifacts/role-guides-98/`。

## 共同建议

两方支持保留经验直接帮助Generator设计标准，分别写给Selector和Generator的操作指南；初始反向知识允许未知，由后续真实案例补齐。但都不认为字段更多就自然有效，也不建议现在把两步生成定成默认。

重要核对：当前Updater已经提示“选择错先查Trigger、应用错先查Principle”；自由文本本来也能写原因和边界。因此新方案不是发现了过去不存在的字段对应关系。值得验证的变化是：角色指导是否清楚、选择和使用过程能否复核、每条修订是否有案例支持，以及这些变化有没有实际收益。

## 推荐的最小经验结构

| 内容 | 要求 | 作用 |
|---|---|---|
| 核心方法 | 必填，一项核验关系 | 说明究竟检查什么，不固定回答策略 |
| 选择指南 | 必填，可简短 | 怎样核查本题是否需要这项方法，不只看主题 |
| 已知不选条件 | 可空 | 什么情况下方法整体不适用 |
| 应用指南 | 必填，可简短 | 怎样将关系落实为评分标准 |
| 已知误用 | 可空 | 方法适用时，哪些做法仍不合理 |
| 离线证据 | 来源、版本、实际轨迹及核对状态 | 让修改可追溯，不交给测试Generator原始答案和偏好标签 |

核心写“核验什么关系”，应用指南写“怎么落实”；不为填满字段复述或编造。Selector看完整运行内容，不能屏蔽核心与应用指导后只按主题选。Generator也能看到选择边界；其重点是应用指南，不把经验条件当本题事实。

两类反向知识应分开：“不要选”和“选了别这样用”不是一件事。可用`null`表示目前未知；具体JSON接口实施前再定，不额外引入一套成熟度等级。未知不等于永远适用，也不自动意味着必须拒选。

失败原因不必另设必填字段。源轨迹和Judge都可能错，强迫Critic写明确why会诱导编造。已有来源分析可以离线保留，标清观察和推测。

## 从不完善候选到后续补齐

以“多条交付的实质差异核验”为例，以下是依据已见问题拟议的完善方式，不是已运行的新版本：

- **初始：**核心方法检查重复凑数；选择指南仅说任务涉及多条内容时考虑；应用指南说核对条目间实质差异。两个反向字段未知。它能用于来源任务，但不承诺覆盖所有边界。
- **观察到SEO错选后：**核对发现“作品有多个版本”只是对象属性，不要求多份文案。收窄选择指南为需要分别交付多条内容，新增“仅说明对象组成而未要求分别创作时，不选”。保留对真实多条交付的有效核验。
- **补充使用边界：**应用应核对task要求的差异，不擅自要求生成对象的新版本，也不限定差异必须表现为某种属性。此项需有实际误用支持；不能把同一案例拆成两个独立证据，或编造第二次下游失败。

若要检查“对象属性是否准确转述”，可以是另一项方法，不应一边排除该场景、一边又在应用指南中要求处理它。内部一致比字段齐全重要。

## 选择与使用说明：已确认方向

用户已同意Selector与Generator分别输出逐经验的选择／使用原因，便于解释与Checker核验。当前Selector仅返回ID，Generator已有整体analysis与逐标准引用；新增的是逐经验依据，不是宣称以前没有记录。说明是可复核线索，不是真值；具体输出接口尚未实现。

## Checker怎样帮助修订

报告中的字段只作为优先调查位置，不直接生成负向规则：

| 核对原始任务、指南与输出后看到的现象 | 优先调查 |
|---|---|
| 适用条件含糊、漏掉区分 | 选择指南或不选条件 |
| 明确条件已有，但执行者忽略 | 选择／应用执行，不必改经验 |
| 忠实执行仍会错罚合理回答 | 核心方法或应用指南 |
| 输出擅自增加数量、格式或结论 | 应用指导是否含糊，或Generator未遵循 |
| 所谓反例本身有事实错误或没有完成任务 | Checker误判或证据不足 |

多种原因可同时存在，无法分清时存为待判案例，不写成确定边界。Judge Checker报错也不能直接用来改经验讨好错误评价。

程序能核对字段、ID、版本、实际可见信息、案例链接和修改记录；不能证明前提成立、指南合理或某一环责任最大。Updater须看task、经验版本、实际选择与标准，不只读Checker的结论。

## 更新规则要改什么

- 修改造成错误的最小充分范围，不机械追加例外。每项指导关联离线证据：指导标识、案例／轨迹、核对状态与理由。区分Checker猜测、已核对观察和仍有争议；核对过也不表示普遍真理。
- 允许连带调整其他字段；核心错误时可以重写核心并重新验证，不把它设成不可改的前提。不能把改核心包装成只补指南，不能直接继承旧Q。
- 保留旧有效例、边界例及没有给Updater看的案例，检查方法保留和正常任务损伤。仅修订已见案例提分不是充分验收。
- 不采用未经验证的“两案例支持”“最多三条负向”等硬门槛。反向指导应归纳共同条件，不变成具体题材黑名单。
- 当前代码已保存召回、选中及选中未引用记录，可以复用；Checker只核对实际引用。可少量抽查未选但接近的候选，发现漏选，不做全池审查。已有日志不是新方案成果。

## 先验证指南，再单独验证两步生成

两方都提醒：“task-only初稿＋经验修订”并非新发现，前面已经试过相关机制且未稳定成功。新增指南不证明第二次调用有效。

可以分阶段准备对照，先不同时改所有因素：

1. **内容与组织：**固定选中集合、模型、单次生成，比较原双字段／修正内容平铺／相同内容按角色组织，并保留无经验对照。后两组的信息与调用预算相同，才能检验角色组织是否有额外作用。Selector另外固定候选集测试适用、边界与有用方法保留，避免混入选择变化。
2. **两步生成：**若值得继续，再让无经验修订与指南修订共享同一份task-only初稿、相同预算；对照单次生成，区分额外调用和经验的作用。
3. **渐进完善：**此后才验证Updater根据下游记录补指南，是否在未参与编辑的任务上改善，并保留有用方法。人工先写完善经验不等于自动学习已有效。

每个变更模块至少20个任务去重的真实输入，覆盖适用、近似但不适用、正常和必要核验。编写指南的案例与验证案例分开，预留20题确认集继续不动。除标准内容外也检查真实回答对的区分，争议保留，不以引用率或模型共识作通过依据。

## 未照单采用的意见

DeepSeek初稿把某些字段称为原结构无法表达，又说缺Selector判定就无法区分原因；追问后收回，承认只是待验证的组织与记录改进。它的SEO演示还曾改动核心却称只改选择，后续又让被排除场景进入应用；已承认不一致。

它曾建议“task只写字数／格式就不选原文核验”，也已更正：人物分析隐含必要事实正确性，不需要用户逐字声明。不能用机械原文匹配取代这种判断，也不恢复填空模板或参数硬绑定。

**当前建议：共同核心＋两角色指南＋可空的两类反向知识＋离线证据，先检验单次直接生成；两步和自动完善分开验证。**这不是已经确定的实现协议，更不是已证明有效。


## 后续讨论：候选必须有实际应用反馈

用户要求先讨论方法，不展开对照实验。新增方向：候选不能只凭经验核对器认可就成为正常可检索经验，还需要实际使用检验；具体准入规则未确定。

核对当前代码：Selector严格只输出selected_experience_ids；Generator已有analysis、逐标准source_experiences及完整请求日志，缺的是每条经验单独的选择依据与使用说明，不应称作完全没有记录。经验核对器也检查合理性、任务外强制要求等内容，不只是格式。当前真正缺口是先memory.add，之后task+C来源应用虽有Judge／执行Checker／可用时的Q反馈，结果却不影响已经完成的准入。

可讨论的改法：候选先暂存，内容核对后仅用于指定验证应用，不参加正常召回；实际被引用并得到可解释的正向应用证据后再决定正式激活。未引用、同判、技术失败或执行存疑不是已证明经验无效，不直接删改。单次来源应用支持初步试用，不证明跨任务泛化，也不证明相对无经验的净收益；正式激活门槛、执行失败处理和Critic接收何种反馈仍待讨论。
