# Critic候选经验生成与应用控制

> 上位文档：[总览](../设计方案.md) ｜ 应用：[Generator](07-Generator对话修订.md) ｜ 实施：[计划42](../plans/42-删除Admission直接应用候选经验.md)

## 1. 触发与预算

仅训练R0有效Judge失败后启动。Critic提出供未来首次生成评分标准使用的经验，不直接修订标准或给Generator普通修订建议。返回私有analysis及0–1条content/trigger，系统分配候选ID；无可信设计动作可返回空候选并结束。

每轮一次业务提案、一次独立应用，最多两轮，共最多两次Critic提案。没有Admission、拒绝反馈或同轮重生成。底层格式/结构纠错单独有限计数。

```text
Critic提出C → 固定原文 → 新Generator(task+固定E+C) → Judge
  成功且采用C：同一候选Fusion，结束
  成功未采用C：任务成功，不入池，结束
  失败：有剩余轮次则以实际失败证据重新提出，下一轮替换C
  空候选：结束
```

输出耗尽消耗当前轮并保留错误，在剩余轮次内可继续；不伪造Judge，不额外增加提案。Judge错误结束本样本后续流程；网络/鉴权、存储、Calculator和程序错误仍fail-fast。

## 2. Critic输入

输入原始task、chosen/rejected、当前有效失败标准及逐项判断、分数/margin和业务轮次。第二轮附上一条候选、实际采用记录和必要前后标准/Judge；无效轮则保留真实错误及最近有效证据。旧私有analysis不代替事实，不再传准入拒绝理由。

这些是Critic诊断证据，不进入Generator会话。候选ID须新颖且不与固定E/前轮候选冲突，候选必须尚未融合。

## 3. 提炼要求

analysis分清任务要求、问题文本、回答事实和Judge判断，定位有证据的设计动作，再完成实例抽象。零分差本身不证明标准有错；只有Judge疑点而没有可信设计动作时可空候选。

公开content描述核验性质、评价维度或重要性安排；trigger只能从生成前task、实际输入、上下文或领域知识识别，范围与content一致。把来源任务的固定实体、数量、时长和答案对照转成语义角色或新task参数。允许必要领域条件、通用参数说明和服务同一目的的协同动作，不以举例词作自动判定。

不保存偏好身份、私有分差、答案片段，不提供本题回答方案，不放宽任务约束或要求程序不支持的部分分/否决/跳过。抽象在提出与应用前完成，成功后不替换成未经应用的清理版本。

角色边界、提示词及真实应用记录用于约束和审计，没有额外语义审核或泄漏过滤器；直接应用不保证候选通用性。

## 4. Judge-aware诊断与经验落实

依据计划44，Critic对照原回答核对Judge理由，区分设计缺陷、表达歧义、执行错误与证据不足。可将合理设计动作表达为更明确、可核验的标准，但不能迁就错误事实。第二轮分析前候选的诊断、方法、实际落实与判断环节，依据新增证据调整方法，避免重复首轮建议。公开经验保留可复用的设计动作及必要领域条件，trigger保持事前可识别。
