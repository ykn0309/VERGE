# Critic候选经验生成与应用控制

> 上位文档：[总览](../设计方案.md) ｜ 应用：[Generator](07-Generator对话修订.md) ｜ 实施：[计划42](../plans/42-删除Admission直接应用候选经验.md)

## 1. 触发与预算

仅训练R0有效Judge失败后启动。Critic提出供未来首次生成评分标准使用的经验，不直接修订标准或给Generator普通修订建议。返回私有analysis及0–1条content/trigger，系统分配候选ID；无可信设计动作可返回空候选并结束。

每轮一次业务提案、一次独立应用，最多两轮，共最多两次Critic提案。没有Admission、拒绝反馈或同轮重生成。底层格式/结构纠错单独有限计数。

```text
Critic提出C → 固定原文 → 新Generator(task+固定E+C) → Judge
  采用C且自身P>N：暂存合格候选，不立即入池
  整体成功：结束轮次，在暂存候选中统一选择
  失败：有剩余轮次则以实际失败证据重新提出，下一轮替换C
  空候选：正常结束，回退之前合格候选（如有）
```

输出耗尽消耗当前轮并保留错误，在剩余轮次内可继续；不伪造Judge，不额外增加提案。Judge错误结束本样本后续流程；请求重试耗尽按计划63隔离；鉴权、存储、Calculator和程序错误仍fail-fast。

## 2. Critic输入

同一样本内采用多轮消息：首轮为system和user，user包含原始task、chosen/rejected、R0标准及逐项判断、分数/margin和业务轮次。保留Critic真实assistant原文（analysis与候选），第二轮在已有消息之后追加一条user反馈，包含上一候选的采用记录、应用标准/Judge及重新分析提案的要求。原任务、回答和R0证据由首轮消息承载，不重复附入反馈。每条反馈中的对象编号仅在该消息内解释。

计划56将消息展示改为逐标准分块：先列问题、权重与来源，再将两侧Judge判定、解释分别置于独立行；保留完整原文和短编号。Judge解释明确标为待核对，不视作事实证明。可读性改动不改变内部Boolean、偏好标签或多轮会话协议。

无效轮追加真实错误及最近有效证据，明确没有新Judge结果；保留收到的真实回复但不把无效候选当作成功提案。历史analysis仅供Critic回顾，必须用实际结果核对，不代替事实。会话由流水线在每个样本内创建，样本之间不共享；技术纠错仍有限，不增加业务轮次。

这些是Critic诊断证据，不进入Generator会话。候选ID须新颖且不与固定E/前轮候选冲突，候选必须尚未入池。

## 3. 提炼要求

analysis分清任务要求、问题文本、回答事实和Judge判断，定位有证据的设计动作，再完成实例抽象。零分差本身不证明标准有错；只有Judge疑点而没有可信设计动作时可空候选。

公开content描述核验性质、评价维度或重要性安排；trigger只能从生成前task、实际输入、上下文或领域知识识别，范围与content一致。把来源任务的固定实体、数量、时长和答案对照转成语义角色或新task参数。每条候选仅一个可独立采用或忽略的原子方法，不把可分别采用的要求捆绑；保留必要领域条件和通用参数说明，不以举例词作自动判定。

不保存偏好身份、私有分差、答案片段，不提供本题回答方案，不放宽任务约束或要求程序不支持的部分分/否决/跳过。抽象在提出与应用前完成，成功后不替换成未经应用的清理版本。

角色边界、提示词及真实应用记录用于约束和审计，没有额外语义审核或泄漏过滤器；直接应用不保证候选通用性。

## 4. Judge-aware诊断与经验落实

依据计划44，Critic对照原回答核对Judge理由，区分设计缺陷、表达歧义、执行错误与证据不足。可将合理设计动作表达为更明确、可核验的标准，但不能迁就错误事实。第二轮分析前候选的诊断、方法、实际落实与判断环节，依据新增证据调整方法，避免重复首轮建议。公开经验保留可复用的设计动作及必要领域条件，trigger保持事前可识别。

计划48：正常收尾时每题最多新增一条，优先合格C2否则C1；资格与整体成功独立。Judge错误不做候选正常回退入池，无效输出不伪造验证。来源信用与候选原文保留，取消Fusion/MERGE。
