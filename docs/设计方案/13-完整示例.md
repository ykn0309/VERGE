# 完整示例：对话修订与下游验证

本例仅演示当前契约，不作为模型效果证据。以题目有两个显式要求为例，Generator 根据 task 输出两个 Boolean 标准，初始重要性均为 5。Judge 对 chosen 给出 `[false, true]`，rejected 给出 `[true, false]`，两侧得分 0.5，初始失败。

Critic 私有 analysis 可以说明候选各自满足了什么；公开 improvement_advice 只指出 task 的核心要求应比呈现形式获得更高重要性，不引用候选。原 Generator 会话保留初始 assistant 回复，追加这段 user 建议，输出完整两条标准及重要性 `[3,8]`，来源为空。系统生成新标准 ID，base 指向 R0，无操作列表或 Executor。

问题文本相同时，Judge 沿用两侧 Boolean 并按新重要性计算：chosen=8/11，rejected=3/11，margin=5/11，本轮成功。若仍失败，第二轮 Critic 针对当前 R1/Judge 建议，原会话继续追加反馈，输出 R2；第二轮的 base 为 R1。第一轮无有效输出时则保留 R0 并记录校验失败。

Reflector 查看原始 task/回答、成功修订前后标准和 Judge 结果、Critic 私有分析及公开建议，最多输出一条“按任务明确主次安排标准重要性”的候选；没有有价值的方法时返回空数组。它不返回支撑操作 ID。Admission 审核可迁移原则和 task-only 适用条件；新经验 ADD 时 Beta(1,1)，置信度 0.5。MERGE 仅追加来源，不增加信用。

后续任务初始 rubric 实际引用该经验时，ExistingCreditAllocator 按既有下游归因公式更新 Beta。训练修订成功不直接增加经验信用；测试只读。Web 可查看 Generator 的真实多轮消息、Critic 公开建议和私有分析、完整修订结果，以及准入/融合和下游证据。
