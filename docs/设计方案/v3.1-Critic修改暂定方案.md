# VERGE v3.1：Critic修改（暂定）

2026-11-13用户暂定。本文记录经验提案阶段的修改，尚未实现或实测。

## 1. 修改目标

v3的Critic看到失败轨迹和chosen／rejected后，可能围绕来源题的回答差异提出具体甚至错误的检查要求。来源题修复成功也不证明经验能够迁移。

v3.1调整为：**先结合人工偏好理由核对Rubric缺陷，有依据且能提炼时才提出经验；无法可靠归因时不生成候选。**

## 2. 输入与分析过程

训练时向Critic提供task、两份回答、各路径Rubric、Judge判断及理由，并加入HelpSteer3的`individual_preference[].reasoning`。本地500题均已保留这些理由，但v3没有传给Critic。

人工理由只提供给训练阶段的Critic；Selector、Generator和Judge继续不看回答偏好标签或人工理由，Judge仍只看当前匿名回答。理由中的Response 1／2必须与转换后的chosen／rejected正确对应。

同一次Critic调用依次完成：

1. **理解偏好依据。**结合task、回答原文及人工理由，确认被重视的评价维度，保留不同标注者的分歧。
2. **核对Rubric。**指出标准遗漏、歪曲或不恰当地强化要求的具体位置，并说明任务或人工理由如何支持这一判断。
3. **决定是否提案。**判断是否能从有依据的缺陷中提炼可复用核验方法；只有理由充分时才生成候选。

分析、决定和提案在一次调用内完成，不新增审核角色。诊断结果怎样编码到输出字段，留待实现设计。

## 3. 何时产生经验

| 观察到的情况 | 处理 |
|---|---|
| 有明确Rubric缺陷，并能提炼核验方法 | 提出候选经验 |
| Rubric已有恰当检查，主要是Judge读错或算错 | 不生成评分标准设计经验 |
| 只能看到最终输赢，无法指出具体缺陷或依据不足 | 不生成候选，并说明不足之处 |
| 有依据的Rubric缺陷与Judge问题同时存在 | 可针对Rubric缺陷提出经验，不要求证明唯一原因 |

“可靠归因”依靠可核对的文本依据，不以模型自报置信度或解释长度代替。Critic不自行更正Judge结果来宣布修复成功。

## 4. 人工理由的使用边界

人工理由用于约束提案依据，不直接复制成未来评分要求。某个回答获得好评的写法，不自动成为所有合格回答的必要条件；理由本身也可能片面、有误或过于笼统，需要与task和回答原文核对。

经验继续描述可复用的适用条件、核心核验方法和生成指南，避免写入来源答案特征、专名、特定数值或固定措辞。标注者意见一致不代表已证明规则普适；不强求每位标注者都提到同一缺陷。

## 5. 状态与验证边界

本次暂定的是提案依据和允许放弃的机制，尚未修改候选准入规则、调用预算或下游信用分配。

Critic仍依靠LLM，人工理由和归因判断均不是真值。候选仍看过来源答案与解释，即时通过仍不能证明泛化，后续独立任务反馈继续必要。更少候选不等于更高质量，需要检查拒绝是否有依据，以及是否遗漏有价值的经验。
